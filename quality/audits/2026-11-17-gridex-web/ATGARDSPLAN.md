# Åtgärdsplan för Gridex Web

Jag genomför rättningarna i avgränsade ändringar med verifiering per fynd. Planen omfattar **174 GW-fynd, 30 kompletterande F-fynd och fem F-åtgärdsnoteringar**, sammanlagt **209 poster**. F135–F139 har föreslagna åtgärder och klartkriterier. Deras ursprungliga fyndtexter saknas, så jag börjar med att bekräfta vilket flöde varje notering avser. F1–F134 kan kompletteras när fyndtexterna finns. [Samlade rapporten](RAPPORT.md)

### Första ändringen

1. Jag läser aktuell `main` i Web och berörd version av OPS-kontraktet. Jag kontrollerar om GW140, GW141 och GW14 fortfarande gäller i den verkliga importvägen med syntetiska fakturor och kundprofiler.
2. Jag fastställer hur importkontraktet skiljer på fullständig leverans, deluppdatering och uttrycklig rensning. Därefter säkrar jag ägarskap och gör beroende skrivningar atomiska. För fält utan beslutad semantik behöver kontraktet klargöras före ändring.
3. Jag kontrollerar rätt kundkoppling, bevarade fält vid deluppdatering och konsekvent lagring vid avbruten transaktion. Jag följer upp historiskt berörda poster i en läsrapport. Eventuell rättning av befintlig produktionsdata behöver en separat granskad åtgärd.

### Beroenden mellan ändringar

- **Pris och katalog.** Först verifierad täckning, prisintervall och källrevision. Därefter villkorad återanvändning och snabbare rendering. Teckningens slutkontroll måste fortsatt kunna fastställa om erbjudandet är aktuellt.
- **Web, mobil och OPS.** När ett kontrakt behöver ändras börjar jag med en kompatibel förändring på tjänstesidan. Jag uppdaterar OpenAPI, genererade typer och berörda klienter i kompatibel ordning. Om gamla mobilversioner använder kontraktet testar jag både tidigare och nytt svar.
- **Databas och köer.** Inför nya fält, index eller uppslag kompatibelt där det går. Kontrollera historiska rader och databasplan innan en ny läsväg blir standard. Lås, idempotens och bolags- samt kundavgränsning verifieras före parallell bearbetning.
- **Samma ändring för överlapp.** GW124/F151, GW155/F160, GW156/F161 och GW157/F164 stängs parvis när båda klartkriterierna är uppfyllda. GW95, GW168, F135, F136 och F153 samordnas kring avbrott i transporten, med en kontroll per flöde.

### Verifiering och status

1. Dokumentera per fynd vilken revision jag kontrollerade och använd status **Öppet**, **Redan rättat**, **Pågår**, **Verifierat** eller **Blockerat**. Ett redan rättat fynd behöver en läsning eller kontroll som visar att klartkriteriet uppfylls. Ett blockerat fynd behöver en konkret förutsättning.
2. Kör riktat test med syntetiska data genom den berörda kodvägen. Verifiera både avsett beteende och felväg där den är relevant. För ändringar över repogränser, verifiera konsumentens och tjänstens kontrakt tillsammans. Kör befintliga tester för berört flöde och lägg till regressionstäckning där den saknas.
3. Kör relevanta kontroller i Web före leverans. `npm run typecheck`, `npm run lint`, `npm test` och `npm run build` används efter ändringens omfattning. Vid OpenAPI- eller migrationsändring kör jag även `npm run api:check:local` respektive `npm run db:migrations:check` och motsvarande kontroller i OPS när OPS ändras.
4. Jämför före och efter med samma testdata och cacheläge. Redovisa antal Auth-, OPS- och databasanrop, överförda byte, väntetid, samtidighet eller köålder enligt fyndet. För p95 krävs upprepade mätningar. Resultat från syntetiska tjänster redovisas som lokala mätningar.
5. När ändringen är klar sparar jag revision, körda tester, utfall och eventuellt kvarstående drift- eller dataarbete på fyndets ID. För data- och kontraktsändringar ska vägen för kompatibel utrullning och återgång vara känd före publicering.
